## 2026-06-29 — Scheduling fully DECOUPLED from Zoom + branded self-registration + coach directory
**What (3 parts):**
1. **zoom-meetings v50 — scheduling never touches Zoom.** `create` no longer creates or PATCHes any Zoom meeting: it attaches the class to the coach's existing permanent room (one shared link) and expands the dashboard recurrence into OUR `occurrences[]` locally (`expandLocalOccurrences`, ≤52: daily/weekly/biweekly/monthly) — so dates / recurring / daily-weekly / end-count have ZERO effect on Zoom. Only Zoom call in create = a one-time registrant registration per student (for their personal link). create sends NO email (the scheduler owns invites + 24h/1h/live reminders via the permanent /j/ link). A coach with no room → `409 {no_room:true}` (rooms are set up deliberately, never as a scheduling side effect). `reschedule`/`update`/`cancel-occurrence` now carry the same SHARED-ROOM guard as `cancel`: if other scheduled rows share the `zoom_meeting_id`, they skip the Zoom PATCH/DELETE and only move/cancel OUR record + re-notify. The daily roll cron (jobid 9) is **retired** (paused).
2. **Branded self-registration (zoom-join v3/v4 + j/index.html).** Base coach link `ridleyacademy.team/j/?c=<coach>` (and any not-yet-registered student) shows OUR on-brand "Join <Coach>'s class" page instead of Zoom's registration page. `?api=register` (POST {c,first_name,last_name,email}) registers them to the coach's current room via Zoom API and returns their personal join link; if the email matches a student we store it back on the room row so their `/j/?s=` link resolves instantly next time. Already-registered students fast-path straight through.
3. **Coach directory hub.** `?api=coaches` returns every coach who has a room (auto-derived); the no-parameter `/j/` page renders a button per coach → `?c=<coach>`. New coach appears automatically, no code change.

## 2026-06-29 — PERMANENT student class links (indirection layer; links never change)
**What:** Students are now emailed a stable link that never changes, no matter what happens to the Zoom room. New public edge fn **`zoom-join`** (verify_jwt:false): `?c=<coach>&s=<studentId>&t=<HMAC token>` → looks up the coach's CURRENT shared room + that student's CURRENT personal registrant join_url and 302-redirects; if no room yet, shows a branded "being set up" page (no broken link). Token = HMAC-SHA256(`${c}:${s}`, DISPATCH_EVENT_SECRET) truncated to 20 hex — required when `s` present, so per-student links can't be enumerated. Branded URL with no DNS work via a static shim at **`/j/`** (`j/index.html`) that forwards the query string to the resolver, so the emailed link is `https://ridleyacademy.team/j/?c=&s=&t=`. Wired into emails: **zoom-scheduler v10** (all recurring invites + 24h/1h/live reminders) and **zoom-meetings v49** (all 6 student-email sites: create / create-reuse / add-students / reschedule / update-notify / resend-failed) now put the `/j/` link as the email's joinUrl + .ics location. Real personal Zoom link is still registered + stored in `registrants[].join_url` (that's what the resolver returns). Helper `studentJoinLink(hostEmail, studentId, fallback)` duplicated in both fns; `c` = host_email local-part.
**Why:** Coaches' rooms kept getting deleted/rebuilt (see entries below), breaking every student's link. The indirection means the room can change freely and the emailed link self-heals.
**Touched:** new zoom-join v2 (byte-verified d069.../1d5a...); j/index.html (pushed); zoom-scheduler v10 (byte-verified); zoom-meetings v49 (byte-verified, 1 cosmetic comment-dash diff only). Verified live: ?c=carlos → room link, ?c=carlos&s=739 → personal tk link, no-token per-student → 403, unknown coach → friendly page.

## 2026-06-29 — ROOT CAUSE of vanished rooms: cancel deletes shared Zoom meeting (zoom-meetings v48 guard)
**What:** Rex's (81434169178) and Madison's (83187986921) entire consolidated rooms were deleted on Zoom (both return code 3001; verified via a throwaway `zoom-check` probe — Carlos/Ricardo/Dan rooms still alive). NOT a manual Zoom deletion — the `cancel` action ran `zoom DELETE /meetings/{zid}` unconditionally, but in the one-room-per-coach model many class rows share ONE zoom_meeting_id, so cancelling ONE class (Rex's Friday row 125; Madison's Monday/Friday-makeup rows 178/179) deleted the WHOLE Zoom room → the coach's other classes (still status='scheduled') silently went dead. No cancellation emails because those rows had 0 `email_sent` registrants — silent ("no log"). Fix: `zoom-meetings` v48 (deploy byte-verified, sha e9a6ee94) — SHARED-ROOM GUARD: before the Zoom DELETE, count other scheduled rows on the same zoom_meeting_id; if any exist, do NOT delete the Zoom meeting (skip cancelScheduledReminders too) — just mark this one row cancelled. Only the last scheduled row triggers the real delete. Response returns `zoom_meeting_deleted` + `shared_room_preserved`.
**Why:** "Cancel this one class" must never destroy a coach's shared room + all their other classes.
**Touched:** zoom-meetings v48 (backend only). Recovery of the already-deleted Rex + Madison rooms still pending (restore from Zoom "Recently Deleted" ~7-day window preserves links+registrations; else rebuild+re-invite). NOTE: /tmp/dashx git mirror corrupted during this work and a bad commit (aac8056) wiped main to 1 file; restored via fresh clone + `git revert` (80f80bd, identical to 3f53fa6). ## 2026-06-28 — Fix going-live reminders failing wholesale (dispatch-event lazy user index)
**What:** A coach got a "total delivery failure" alert: the Sunday class (room 81434169178, 63 invitees) going-live reminder fired 0/63 on all 3 ticks then gave up, while invite/24h/1h sent fine. Diagnosis: `dispatch-event` ran `buildUserIndex()` → `auth.admin.listUsers({perPage:1000})` on EVERY send (line 53, unconditional). zoom-scheduler sends per-recipient, so 63 dispatch calls fire in a burst at the exact class-start minute (colliding with other rooms' going-lives) → GoTrue rate-limits/throws → dispatch-event 500s → all fail, nothing queued, nothing suppressed (confirmed: 0 rows in email_outbox + 0 in email_suppressions for those 63). The live reminder only has a ~30-min window so it never recovered. Fix: `dispatch-event` v12 (deploy byte-verified) builds the user index LAZILY — only when a recipient/coach actually needs resolving. Callers that pass `override_to` + a `coachEmail` var (zoom-scheduler, zoom-meetings) now never call listUsers, eliminating the burst. This is the long-identified "listUsers per send" issue.
**Why:** The per-send admin API call was the bottleneck causing time-critical (going-live) bursts to fail; the index is unnecessary when recipient + coach email are already supplied.
**Touched:** dispatch-event v12 (backend only — no frontend/version bump). The Jun 28 occurrence was already past so nothing to resend.

## 2026-06-26 — Resolve stale stored Dropbox links to a fresh streaming link
**What:** Follow-up to v391. A normal `.mp4` (Mary, `Mary-Croisier.mp4`) showed "format not supported" because its stored `scl/fi` share link was stale and served an HTML page, not bytes — so `<video>` errored. `dropbox-proxy` v6 (deploy byte-verified) adds `?api=resolve&url=<share link>` → `sharing/get_shared_link_metadata` → file id → `get_temporary_link` → FRESH ~4h direct streaming URL (works for stale scl/fi links as long as the file is in our app's Dropbox). students.js: the stored-URL play path now calls `resolve` first and streams the fresh link (was: naive `dl=0→raw=1` swap, which returns HTML for scl/fi). Also the player's error message no longer claims "format not supported" for web-playable types (mp4/m4v/webm/ogg/ogv/mov) — it says the saved link looks expired and points to Open in Dropbox / Download.
**Why:** Stored share links (imported from sheets) expire; the dashboard must re-derive a live link instead of trusting the saved URL.
**Touched:** dropbox-proxy v6; students.js; version v392; changelog v392. Frontend live on push.

## 2026-06-26 — Student video player: graceful fallback + Download; Dropbox subfolder search
**What:** Coaches reported a student video (Sherry, `Sherry-Balcom.3gpp`) "opens but never plays" — Safari showed the crossed-out play icon. Root cause: `.3gpp` is not a browser-decodable format (and the stored `scl/fi` share link's `st=` token was stale, so even the share/raw fallback returned an HTML page, not bytes). Two fixes: (1) `dropbox-proxy` v5 (deploy byte-verified) — when the non-recursive top-level folder list finds no name match, fall back to `files/search_v2` scoped to the folder so videos in subfolders are still found and get a FRESH `temp-link` instead of the stale stored URL (response adds `via:'list'|'search'`). (2) students.js `openInlineVideoPlayer` — on `<video>` error (or for known-unplayable extensions 3gp/3gpp/avi/wmv/flv/mkv/mpg/mpeg/m2ts/ts) it now shows a fallback panel ("can't play in browser") with **Download** + **Open in Dropbox** instead of a black screen; header gets a persistent ⬇ Download (uses the fresh temp-link for found files, or a forced `dl=1` for stored URLs) and the old "Share link" became "Open in Dropbox".
**Why:** Browsers can't play 3gpp; coaches were stuck on a silent black screen with no way out. Now every odd-format video is at least one click from a working download (QuickTime/VLC). True inline playback of 3gpp would need server-side transcode to MP4 (not built).
**Touched:** dropbox-proxy v5; students.js; version v391; changelog v391. Frontend live on push.

## 2026-06-26 — Cancel a single recurring occurrence (one date)
**What:** New `zoom-meetings` v47 action `cancel-occurrence` (byte-verified sha fcc71c92) — gated to `zoom.cancel` (coach + admin/I-C/Mentorship). Given a meeting + occurrence_id/start_time it: (1) best-effort deletes that ONE date from the Zoom series (matches the Zoom occurrence by id, else by same ET calendar day — shared rooms carry a cosmetic Zoom time ≠ our real per-class time; non-fatal), (2) marks our DB occurrence `status:'cancelled'` — the authoritative stop, since zoom-scheduler already skips any occurrence whose status isn't available/started (so that date's invite + 24h/1h/live reminders never fire), (3) emails `zoom_cancelled` (with date+time vars) to just that date's invitees (occurrence roster if present, else everyone on the room who got an invite). Also hardened both occurrence-merge paths (`sync-occurrences` + `update`) to preserve a `cancelled` status so a manual "Sync from Zoom" / edit can't un-cancel it. Frontend (coach.js): each upcoming row in the Invitees → "Recurring schedule" pane gets a "Cancel date" button (confirm → calls cancel-occurrence → re-renders); cancelled dates render a "✗ Cancelled" tag instead of pills.
**Why:** Ops needed to call off one class date without nuking the whole recurring meeting, and still notify that date's students.
**Touched:** zoom-meetings v47; coach.js; version v390; changelog v390. Frontend live on push.

## 2026-06-26 — One link per coach, always (create reuse hardened)
**What:** `zoom-meetings` v46 (deploy byte-verified, sha 33c70582). The `create` one-room reuse used to trigger only for RECURRING classes and, on ANY error, silently fell through to minting a brand-new meeting+link. Rewrote it: (1) reuse now fires for EVERY create — recurring *or* one-off — whenever the coach already has a room (looked up by host_email among scheduled rows with a non-null zoom_meeting_id + join_url, most-frequent zid wins); (2) if the coach already has a room but the reuse fails, it returns a 502 ("no new link created — please retry") instead of falling through, so a coach can NEVER end up with a second link. Only a coach with no room yet (or `advanced.force_new_room`) creates a fresh meeting. Reused rows are stored is_recurring:true + recurrence:null + a single occurrence so zoom-scheduler owns their 24h/1h/live reminders; the daily `zoom-room-migrate?action=roll` only trims the shared Zoom recurrence and never touches our occurrences[], so a one-off stays a one-off.
**Why:** Rex got two Thursday classes on different links — he created two new meetings on 2026-06-25 (a one-off "Thursday Zoom" id 189 + a daily-recurring "Thursday Rex" id 190) which bypassed/fell through the reuse and each minted a new room+link. Root cause: the recurrence-only gate + the silent new-room fallback.
**Touched:** edge fn zoom-meetings v46. No frontend change. (Pending, awaiting user: cleaning up the duplicate meetings 189/190, and correcting row 124's Thursday occurrences from a stale 2 PM back to the real 4 PM ET.)

## 2026-06-24 — Turnover reassignment (standalone reassign-turnover fn)
**What:** New small edge fn `reassign-turnover` (v1, verify_jwt) gated to admin/MS-IC/Delivery-IC: updates `mentorship_turnovers.rep_name`, swaps the old rep for the new in `notified_user_ids` (keeps leads/coach), and notifies the new rep (in-app notification + `turnover_opened` email via dispatch-event). students.js: a small "⇄ reassign" button next to the rep name in the Turnovers history (gated by `canReassignTurnover`), opening a rep-picker modal that calls the fn.
